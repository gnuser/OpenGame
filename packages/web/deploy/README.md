# OpenGame 受邀内测部署

部署对象是完整的创作服务，包括 Next.js 工作台、PostgreSQL、制作 worker、Git 数据和 Docker 构建环境。仅上传前端静态文件不能提供游戏创作。首批采用单主机、单 worker，为少量受邀成员提供创作、修改和分享试玩。

## 域名与运行位置

`xiajuan.app` 已有 Cloudflare Pages 网站。使用两个地址：`studio.xiajuan.app` 用于工作台，`studio-games.xiajuan.app` 用于游戏。当前部署主机为 `170.106.113.23`。该主机已有 Xray 占用 443，两个游戏域名经精确 SNI 规则转发到现有 Nginx 的 8443 TLS 入口，再转发到回环应用端口。根域名站点及其他业务继续保留。旧主机 `43.131.252.64` 目前仅为这两个域名转发到新站，旧制作服务已经停止并取消开机启动。

新主机的 Node.js 22 位于 `/opt/opengame-node/bin/node`，保留系统原有 Node.js 18；正式 systemd 服务使用前者并调整 PATH。平台账号 UID 为 1006，Rootless Docker socket 位于 `/run/user/1006/docker.sock`。通用示例中的 `/usr/bin/node` 需要按实际安装路径调整。正式服务还通过 `InaccessiblePaths` 隐藏原有业务配置、其他用户目录及网站目录，防止平台进程读取无关凭据。

| 文件                            | 用途                                           |
| ------------------------------- | ---------------------------------------------- |
| `studio.env.example`            | 两个入口、数据库、数据目录和签名密钥的配置样例 |
| `Caddyfile`                     | 两个 HTTPS 入口代理至本机 4190 和 4191         |
| `nginx-http.conf`               | 已有 Nginx 主机的证书验证入口和 HTTPS 跳转     |
| `nginx-https.conf`              | 证书签发后的两个 HTTPS 入口                    |
| `opengame.service`              | Linux 服务启动、停止与异常重启                 |
| `opengame-codex-bwrap.apparmor` | Ubuntu 24.04 中固定 Codex 程序的命名空间权限   |
| `opengame-cert-renew.sh`        | 本站证书续期后检查并重新加载 Nginx             |

建议首台服务器使用 2 核、4 GiB 内存起步，并为模型执行和 Git 历史预留独立磁盘空间；这只是起步配置，尚无并发容量测试。Docker 验收容器限制为 1 CPU、1 GiB，制作队列串行运行。

## 服务准备

使用专门的 `opengame` 系统账号管理 `/srv/opengame` 源码和 `/var/lib/opengame` 数据。此账号不加入 sudo 或 Docker 高权限组。需要 Node.js 22、Git、PostgreSQL 客户端与数据库、Rootless Docker、Nginx（新主机也可选择 Caddy）、`/usr/bin/curl`，以及已登录的 Codex CLI。

按照 [Docker 官方 Rootless 安装说明](https://docs.docker.com/engine/security/rootless/) 安装服务账号自己的 Docker，启用该账号的 linger 和用户级 `docker.service`，将其 Docker context 设为 `rootless`。平台服务必须设置 `HOME=/var/lib/opengame`，以便读取此 context；无需传递高权限宿主机 Docker socket。确认 `docker info` 显示 `rootless`、cgroup v2 和 systemd，再以该账号构建镜像。当前主机服务账号 UID 为 1006，socket 位于 `/run/user/1006/docker.sock`；旧主机的 UID 为 1002，其他主机应使用其实际 UID。

Codex 必须支持 `permissions` 命名配置、`--strict-config` 和 `--ignore-user-config`。当前验证版本为 `0.162.0-alpha.17.2`，安装在 `/opt/opengame-tools`；上线前在目标主机执行下方权限验收。安装路径不同应修改 `OPENGAME_CODEX_BIN` 和 systemd 的 `ExecStart`。模型控制进程使用服务账号的登录，不需要成员配置自己的模型。

Linux 下若原生 Codex 位于系统最小读取范围之外，通过 `OPENGAME_CODEX_SANDBOX_EXECUTABLE` 指定原生二进制文件本身。不能填写目录、JS 启动器或链接。权限规则只为该文件增加只读权限，服务账号 HOME 和相邻项目仍禁止读取。平台会在生成前创建 `.agents`、`.codex`、`.aws` 空目录，让 Bubblewrap 正确识别拒绝挂载的目录类型；若已有同名链接或普通文件则拒绝运行。

Ubuntu 24.04 保持全局非特权 user namespace 限制开启。将示例 AppArmor 配置中的路径对照实际安装位置，安装到 `/etc/apparmor.d/` 并使用 `apparmor_parser -r` 加载，仅让固定、root 拥有的 Codex 程序和内置 Bubblewrap 创建自身命名空间。不要关闭系统 AppArmor。升级 Codex 或变更路径后重新执行 Linux 沙箱测试与真实模型权限验收。

在仓库根目录安装依赖并准备固定运行镜像：

```sh
npm ci --workspace=@opengame/web --include-workspace-root=false --ignore-scripts
npm run runtime:prepare --workspace=@opengame/web
npm run build:production --workspace=@opengame/web
```

创建平台专用数据库和最小权限的拥有者。不要向公网开放 PostgreSQL 或 Docker socket。将样例配置复制到 `/etc/opengame/studio.env`，文件只允许服务账号读取，填写实际数据库连接和两个 HTTPS 地址，并生成独立随机签名密钥。不要把真实配置提交到 Git。

以服务账号在 `packages/web` 目录执行：

```sh
node --env-file=/etc/opengame/studio.env --import tsx scripts/check-generator.ts
node --env-file=/etc/opengame/studio.env --import tsx scripts/invite.ts create '首位内测成员' 30
node --env-file=/etc/opengame/studio.env --import tsx scripts/start.ts
```

权限验收会调用一次模型，只使用人工测试文件，验证当前项目可写、相邻项目和共享临时文件不可读、项目命令不可连接临时本机服务。正式启动还会检查构建产物、Docker 镜像、数据库和实际文件隔离；检查失败不会切换到宽松运行方式。

确认主机运行正常后安装 `opengame.service`，按实际路径调整配置。保持后端只监听回环地址，反向代理应保留请求 Host。Cloudflare 如代理这两个域名，应采用验证源站证书的 HTTPS 连接，并跳过工作台 API 与游戏资源缓存。游戏路径包含访问凭据，游戏入口同时关闭访问日志与可能记录请求路径的代理错误日志。

已有 Nginx 的主机先安装 `nginx-http.conf`，创建 `/var/www/opengame-acme`，测试配置后重新加载 Nginx。添加两条 DNS only 的 A 记录：`studio` 和 `studio-games` 均指向目标主机，当前为 `170.106.113.23`。确认公网解析正确后，通过现有 Certbot 账号申请证书：

```sh
sudo certbot certonly --webroot -w /var/www/opengame-acme \
  --cert-name opengame-studio \
  -d studio.xiajuan.app -d studio-games.xiajuan.app --non-interactive
```

证书签发成功后，再按主机实际监听端口调整并安装 `nginx-https.conf`，测试、重新加载 Nginx。当前主机将示例中的 443 改为 8443，443 仍由原 Xray 处理，两个域名的精确转发规则写在实际生效的 `09_routing.json` 中。检查证书是否存在时使用 `sudo test -f`，普通部署账号无法遍历证书目录。等待重新加载完成后验证域名的 HTTPS 连接，不得跳过证书校验。

续期使用同一 webroot。将 `opengame-cert-renew.sh` 安装为 root 拥有、权限 755 的 `/etc/letsencrypt/renewal-hooks/deploy/opengame-reload`，并确认 `certbot.timer` 已启用。该钩子只在 `opengame-studio` 证书续期后检查并重新加载 Nginx，不改变其他证书的处理。不要在已有 Nginx 占用 80/443 的主机同时启动 Caddy，也不要覆盖其他网站的配置。

## 成员与作品

每人一个访问码，默认有效 30 天；数据库仅保存其哈希。创建命令将原码写入数据目录的 `invitations/<成员ID>.txt`，不会打印到服务日志。通过私下渠道交给对应成员。登录会话有效 7 天，每位成员最多保留 5 个设备会话；停用成员立即撤销会话和试玩凭据，并请求取消未完成的制作。

以下命令同样在 `packages/web` 下、以服务账号执行：

```sh
node --env-file=/etc/opengame/studio.env --import tsx scripts/invite.ts list
node --env-file=/etc/opengame/studio.env --import tsx scripts/invite.ts disable <成员ID>
```

默认每人最多 10 个项目、滚动 24 小时内 10 次制作、累计 100 次制作，同时最多一个排队或制作中的任务。失败和取消也计入额度。额度目前由管理员在 `studio_users` 中维护，没有管理后台。

公共知识维护者在服务端环境文件中通过 `OPENGAME_KNOWLEDGE_REVIEWERS` 显式列出已有成员UUID，逗号分隔，重启后生效。为空时普通成员仅能贡献自己的经验和查看已发布知识，不能审核、触发复验、发布或回退。不要在浏览器或公共配置中提供修改维护者名单的入口。

能力升级页为 `/evolution`。固定规则样例和检查器在 `benchmarks/popular/`，必须随平台源码一同部署；运行 `npm run evolution:check --workspace=@opengame/web` 可验证现有容器镜像，无需重建镜像。新的数据库表由启动迁移追加，现有游戏无需迁移。公共版本、审核与复验证据均在数据库中，现有全量备份包含这些表。版本编号与固定制作规范0.1.0分开管理。

首次迁移本机已有作品时，项目仍保持无所属成员。确认归属后显式执行 `invite.ts claim-local <成员ID>`，将所有尚无归属的历史项目分给该成员。新成员看不到其他成员的项目、对话和源码；分享页只提供当前发布版本，玩家也必须先受邀登录。退出或停用账号后，其游戏资源链接随之失效。

## 备份与恢复

备份包含数据库、每个项目的 Git 仓库和不可变游戏产物。不会复制模型登录、真实环境文件、邀请原码或临时生成目录。环境配置和模型登录需要独立管理；备份包含私人项目数据，应保存在受限的独立存储中。

完成或取消制作任务，停止 `opengame` 服务，等待至少 15 秒；数据库保持运行。以下示例要求备份父目录已经存在且服务账号可写，目标目录尚不存在：

```sh
node --env-file=/etc/opengame/studio.env --import tsx scripts/backup.ts /srv/opengame-backups/2026-10-14
```

备份命令拒绝仍有活跃 worker 或未完成任务的状态，导出数据库并复制仓库和产物，逐版本核验产物哈希和 Git 提交，最后写入 `manifest.json`。本阶段采用停机备份；备份期间不要启动服务或运行修改数据的管理命令。

恢复始终先使用新数据库和新数据目录：

1. 对照 `manifest.json` 验证 `database.dump` 的 SHA-256，核验每个版本的产物哈希与 Git 提交。
2. 用 PostgreSQL 工具创建空数据库，通过 `pg_restore --exit-on-error --no-owner --no-acl` 导入备份。使用受限的 PostgreSQL 密码文件或子进程环境传入凭据，不在命令行中写密码。
3. 将 `projects/` 和 `artifacts/` 复制到新数据目录，并确保服务账号拥有这些文件。不要覆盖正在使用的原数据库和目录。
4. 在恢复后的数据库清空 `studio_sessions` 与 `studio_login_limits`，使旧会话失效；保留成员、作品和版本。
5. 在恢复环境的配置中填写新数据库和目录，重新配置模型登录与签名密钥，启动服务。确认成员重新登录、历史版本、试玩和源码提交都可用，再切换入口。

数据库、仓库和游戏产物应来自同一份停机备份。只恢复数据库会缺失源码与游戏文件；只复制游戏文件无法恢复对话、版本关系和成员归属。

## 上线验证与范围

发布入口前需要在目标主机完成：权限验收、邀请登录、两个成员间的项目隔离、一次真实制作与发布、退出后资源失效，以及一份可恢复的备份。首次接入域名还要验证 HTTPS、主机地址检查、两入口互通和浏览器游戏加载。

当前适合少量受邀成员。构建检查通过只说明基本运行、输入和重开正常，不代表玩法质量或完整触屏适配。模型执行没有每任务的内存与磁盘硬配额，原始生成工作目录尚无自动保留策略；上线后需观察磁盘和模型额度。支付、开放注册、多人联机和其他平台发布尚未启用。
